# Agent Note：内置 pi-ai 未随附的提供方路由

Status: implemented

[English](2026-09-14-bundled-pi-ai-provider-catalog.md) | 中文

## 问题

`dsh-llm-pi-ai` 把 pi-ai 的已安装目录当作提供方默认值的唯一来源。因此 pi-ai 未随附的路由必须完整声明，而列表端点不会报告的两类事实对该路由始终不可得：

- **上下文与输出容量。** 模型会解析到路由的 `defaultContextWindow`（262,144）与 `defaultMaxTokens`（32,768）。部署 Ollama Cloud 的 `deepseek-v4.1-flash` 时，一个实际以 1,048,576 提供服务的模型只得到 262,144 的窗口，于是压缩与上下文计量按端点实际接受量的四分之一来规划。输出上限比"保守"更糟：端点会直接拒绝高于其自身上限的 `max_tokens`，所以猜得过高的值不是被钳制，而是让请求失败。
- **推理等级。** 目录中不存在的模型没有 `thinkingLevelMap`，因此 `resolveModelReasoning` 报告 `reasoning: false`，模型选择器完全不提供 effort——尽管该端点对其服务的每个模型都接受推理参数。

把提供方声明为手工路由并不是修复：它把同样的事实搬进每个部署的 `cordis.patch.yml`，需要手工逐条复制，并在服务更换模型时再次复制。

## 决策

`dsh-llm-pi-ai` 在 pi-ai 之外随附第二个目录数据来源，位于 `src/bundled-catalog.ts`。它携带 **Ollama Cloud**（`ollama-cloud`）：端点、协议格式，以及每个模型一条包含上下文窗口、输出上限、输入模态与推理能力的条目。该键命名的是云服务，因此本地 Ollama 服务器仍是普通的手工声明路由，使用部署赋予它的任意 id。

内置数据是目录*数据*，不是 pi-ai 的 `Provider`。`catalogModels()` 像对待已安装路由的 `getBuiltinModels()` 那样从它作答，而 `catalogProvider()` 对内置键仍返回 `undefined`——该函数返回的是可服务请求的提供方，而内置数据不携带协议实现。`resolveProfiles()` 在解析前从内置数据为内置路由补上 `api` 与 `baseURL` 默认值，因此仅声明凭据的 profile 即可服务，而声明了其中任一字段的 profile 仍然优先：把内置路由指向代理正是这些字段的用途。

配置界面读取的是 `catalogProviderIds()`，它现在返回已安装目录，其后是内置路由。因此内置路由会出现在 Models 页面的提供方选择器中，并被报告为 `declared: false`，因为本适配器确实描述了它——`declared` 回答的是路由默认值是否来自任何来源，而不是该来源是否为 pi-ai。`discoverModels()` 对内置路由直接由内置数据作答、不发网络请求，理由与它对已安装路由由 pi-ai 注册表作答相同。

### 推理等级属于目录，而非配置

内置模型的条目携带显式推理等级。每个等级映射到自己的线上拼写，而模型无法被请求的每个等级都被固定为 `null`，因为 pi-ai 的默认化是不对称的——缺失的键对五个基础等级意味着"支持"，对 `xhigh`/`max` 却意味着"不支持"。

`off` 是唯一因模型而异答案的等级，也正是内置数据按模型存储 `supportsOff` 而非假定单一行为的原因。Ollama 的推理参数是一个取值（`none`），而不是省略字段，而省略它会选中模型自身的默认——此处每个模型的默认都会思考。无论被请求什么都会持续产出推理输出的模型声明 `off: null`；这既让选择器不提供该等级，也让 pi-ai 在渲染请求时省略该参数，因此控件绝不会声称模型做不到的事。这是实测而非依据文档推断：`/api/show` 会报告每个模型的 `thinking.values` 列表，但那些是该模型偏好的等级，端点接受并作用于更宽的集合。

### 取值读自服务

内置数据中的容量、模态与推理行为都读自 Ollama Cloud 的 API，而非从 README 转录：`contextWindow` 来自 `/api/show` 的 `<architecture>.context_length`，输出上限来自 Responses 端点接受的最大 `max_tokens`，`input` 来自 `capabilities`，推理字段则来自请求各等级时是否真的返回推理条目。

`deepseek-v4.1-flash` 携带其 393,216 token 的输出上限，这也是其端点接受的最大 `max_tokens`。

## 考虑过的替代方案

- **要求部署自行声明这些事实。** 拒绝，因为这正是现状，并且会把某个服务的逐模型快照放进每个部署的配置文件。容量错了 4 倍的提供方会让压缩与上下文压力判断也错相同的倍数，而每个部署都要各自且无声地承担这份代价。
- **由一个部署挂载的插件来贡献路由。** 拒绝，因为 harness 尚处 pre-stable，而如此常见的路由应当与提供它的适配器放在一起。需要另一组事实的第三方可以把手路由声明为手工路由，这里没有任何改动会影响这一点。
- **在配置时询问 Ollama 的 `/api/show`。** 拒绝将其作为这些事实的来源：端点需要模型 id，因此无法为添加提供方的选择器回答"存在哪些模型"，而且它既不报告可接受的 `max_tokens` 上限，也不报告请求 `off` 是否会改变行为。它是刷新时的有用维护手段，而不是运行时依赖。
- **把该路由建模为注册表中真正的 pi-ai `Provider`。** 拒绝，因为 `catalogProvider()` 的结果会被复用并用于流式传输。内置提供方将不得不携带 API 实现，而这正是内置数据所要避免的耦合；`buildProvider()` 还会静默复用一个 stream 成员会抛错的提供方。
- **对每个推理模型都声明支持 `off`。** 拒绝，因为有两个在服务中的模型（`gpt-oss:20b`、`gpt-oss:120b`）在被请求 `none` 时仍会返回推理输出。在那里提供关闭开关会呈现提供方会忽略的设置，而这正是该 seam 的推理元数据要防止的失败。

## 后果

想要使用 Ollama Cloud 的部署只需声明它与其凭据，即可得到一条可工作的路由；该提供方像已安装提供方一样出现在 Models 页面的提供方选择器中。内置数据未命名的路由，或其 profile 声明了自身 `api`、`baseURL` 或 `models` 的路由，行为与之前完全一致——手工路由没有任何变化。

内置数据是某个会变化的服务的快照。在此构建之后加入 Ollama Cloud 的模型会依据路由的 `defaultContextWindow` 与 `defaultMaxTokens` 解析，且在该条目被加入前不提供推理等级；被服务下线的模型在此之前仍会列出。包 README 的 `Known Limitations` 说明了这两点。

新增内置路由意味着同时加入其事实与钉住这些事实的测试。刷新时需要特别留意的是推理等级映射：模型的 `supportsOff` 是线上观测结果，而不是服务发布的字段，因此必须重新实测而不能照抄。
