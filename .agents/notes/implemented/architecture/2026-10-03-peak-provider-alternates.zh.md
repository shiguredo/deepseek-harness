# Agent Note：模型条目的 peak 提供方替代

Status: implemented

[English](2026-10-03-peak-provider-alternates.md) | 中文

## 问题

同一模型可以通过两个提供方抵达的部署，希望正常时段使用其中一个、peak 时段使用另一个——例如白天用 Ollama Cloud、夜间用 OpenCode Go——而模型 id 与推理强度保持不变。现有的两个归属方都无法表达这一点。

- **提供方选择是按请求的，但配置是静态的。** `dsh-llm` 依据 `LlmCallConfig.provider` 选择适配器，而 `dsh-llm-pi-ai` 在解析模型时就固化了每条路由的 `baseURL` 与 `api`；只有 `apiKeyEnv` 按请求解析。因此一个模型条目无法点名两个端点。
- **在 agent loop 层路由会改变路由身份。** `agent/request` 监听器可以改写 `provider`，但 Session 日志、模型选择器以及模型切换通知都会跟随被改写后的提供方：选择器会切到替代提供方的分组，而 `installModelSelection` 会在 peak 窗口的每一步追加「model changed」通知，因为已装配的选择永远无法与记录的请求头一致。

## 决策

`dsh-llm-pi-ai` 的模型条目接受一个可选的 `peak` 列表，按优先级顺序点名从 pi-ai **已安装目录**解析出的目的地，并可选带 `model` 与 `apiKeyEnv`。这些目的地生效的时段属于目录数据而非配置：内置模型携带其提供方公布的高峰窗口（`BundledModel.peakWindow`），解析时把该窗口与配置的目的地组合起来。

价格政策不是部署的偏好。写在配置里的窗口可能与提供方实际计费不一致——一个漏写星期几的 `21:00`-`03:00` JST 窗口会把请求从 Ollama 按低峰价计费的周末转走，而配置本身无法说明哪种读法正确。把时段集中到一处即可消除这类分歧：配置说明请求去往哪里，目录说明什么时候。

适配器在每次请求中于凭据 await 之前、在 `prepareCall()` 与 `stream()` 里各解析一次有效路由。处于匹配窗口内时分派候选的目录描述符——候选点名了模型就用它，未点名则用被路由模型自身的 id——否则分派路由自身的描述符。报告的提供方、模型 id 以及 Session 日志都保持配置路由不变，因此该切换在适配器之上不可见：选择器仍只有一个提供方分组，不会出现模型切换通知，且由于两条路由由同一个适配器实例服务，replay 状态得以保留。

组合出的窗口是本地的 `HH:mm`，`from` 含端点、`to` 不含端点，按各自的 IANA `timeZone` 读取；`to` 早于 `from` 表示跨午夜。目录按提供方自身的表述记录窗口——Ollama Cloud 的是 `mon`-`fri` 的 UTC `12:00`-`18:00`——因此无需手工维护换算后的值。目的地按配置顺序解析，只有靠前的候选无法提供服务时才使用靠后的。

### 候选取自目录数据，而非其他路由

目的地必须是已安装的 pi-ai 提供方，且目录声明它服务于窗口发送给它的模型——目的地自带 `model` 时用该模型，否则用被路由模型的 id；配置会拒绝内置路由、手工声明路由，以及目的地不描述的模型。因此窗口可以把请求换到另一个模型（包括同一提供方的另一个模型），而不只是把同一个 id 换到另一个端点。适配器会为每个被引用的候选向其快照注册一个目录提供方，并为它构建一份默认执行 profile，因此部署不必再把这个替代方声明为可选路由。凭据取自目的地的 `apiKeyEnv`，与路由自身的一样按请求解析。

本构建未随附窗口的模型在加载时拒绝目的地，因为配置无法回答的时段是一条永远不会触发的路由规则。仍带旧形状时段的条目仍能通过校验——schemastery 会透传未知键——而解析会用内置窗口覆盖它，因此过期的时段无法重新引入本记录消除的分歧。

目录通过 `LlmModelInfo.routing` 携带每个窗口的服务提供方与模型，因此 Web 模型选择器在窗口生效时会显示该提供方并标注为自动。

## 考虑过的替代方案

- **`agent/request` 监听器**——被拒绝，因为它会改变 Session 日志中的路由身份、在每一步触发模型切换通知，并在选择器中显示替代提供方的分组。
- **带自有适配器的新逻辑路由**——被拒绝，因为它会重复目录提供方已经拥有的协议处理。
- **本地转发代理**——被拒绝，因为 Ollama Cloud 使用 `openai-responses`，而 OpenCode Go 使用 `openai-completions`，代理需要转换协议并多出一个待监管的进程。
- **点名另一条已配置路由作为替代方**——可行，但候选取自目录可以避免选择器为同一模型多出一个分组。

## 后果

- Session 日志记录配置路由，而不是实际处理请求的后端；该细节只存在于提供方自身的用量记录中。
- 容量与推理等级跟随候选的目录描述符，因此候选容量不同的窗口会在每次切换时改变 `request/context`。
- 刻意不提供跨提供方的失败回退：失败的请求不会在另一个目的地上重试。
- 本构建未随附其高峰政策的提供方无法被排程；要新增一处，需把其公布的窗口加入目录。
- 注册时捕获的重试策略属于配置路由，而非候选。
